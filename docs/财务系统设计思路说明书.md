# 财务系统设计思路说明书（多 AI 协同项目）

虽然是说明书，就不整的很严肃，随便说点想法吧。

我设计的多 AI 协同系统可能和 SoC 的主题差别比较大，因为这个系统是我在 SoC 前就想做的，可惜大一下都在忙着转专业和备考六级，并没有很多时间考虑这个构思。

一切的起因是因为我看到做财务管理的老妈在做账方面总是花非常多的时间，经过观察后觉得，很多事情都是重复，或者技术含量不是很高的摘录、整理工作，就想整个法子能够减轻一些老妈的负担。况且，很多公司对财务这一块可以说一窍不通、毫无章法，做这样的系统也能对各项目的了解情况和所有文件的归纳整理有所裨益。一开始的我认为任何系统，只要有固定的输入，有严格的函数，就能有精确的输出，而财务是很讲究严谨和依据的，这也是这个系统能够在理论上成立的依据。当时也正好发布了 SoC 的题目，觉得多 AI 协同是个不错的法子，就开始构思设计。

以下是我最初构想的大致结构，也是整体的设计思路。

## 1. 输入（input）

财务类的文件有很多，可以是表格，可以是 PDF 图片，也可以是 Word。将文件中的有效信息提取出来是很重要的事情。表格和 Word 中的文字可以直接被提取，但是图片不行，我们需要 OCR 来扫描图片，转换成文字。然而当时的我查询了一些公司的要求，这也使得对接下来的设计思路有了很重要的变化。

## 2. 脱敏（desensitization）

根据《生成式人工智能服务管理暂行办法》和《个人信息保护法》等，个人或者公司数据未经允许，是不允许上传 AI 的，特别是公司会非常注重数据保护，很多公司都只会部署本地训练的大模型进行工作。这说明公司对脱敏有比较大的要求。这就使得我必须将 OCR 部署在本地，将扫描后的正文脱敏之后再发送给 AI。然而，如何用传统算法精确地脱敏是比较大的难题。

"用传统算法精确脱敏"这件事，真做下去才发现它的难点不在"认出身份证号"，而在**边界**。

身份证、银行卡、税号、账号、手机号、日期，这些都有比较硬的形态，正则能吃掉绝大部分。真正难的是公司名和人名：没有固定长度，没有固定词尾，还经常和别的字粘在一起。OCR 出来的东西更离谱——"某某城市服务有限公司（盖章）"整段连在一起，"法定代表人：张某某（签字）"后面跟着一串证件号，表格里的"株""20 年 月 日""¥789814.72 元""项目付款进度"这些标签、单位、金额，长得都挺像"实体名"。

其实脱敏也是有本地模型的，然而问题是 OCR 已经把显存吃满的情况下，另一个本地脱敏模型没有办法同时进行，而如果分步进行，时间则会过长。况且脱敏模型的大小注定了它只容许一些通用的语义脱敏，对于特定语义的脱敏可能依然做得不够完善。这样看来，假如能够只依赖算法直接脱敏，而准确率不低的情况下，所开销的时间和对显存的要求也会降低不少。

早期版本把很多东西统统登记成了公司和人员编号，结果编号语义被污染——同一个编号既指过公司又指过计量单位，AI 看到编号就据此"推理"，编出来的结论还特别自信。尤其是表格一块：Kv 表只能登记成键值对，对于合并单元格的表头会被登记为值为 0 的键，这导致用算法判断时把键一并判进脱敏中——实际上我们只需要查看正常键下的值。

后来稳定下来的做法是这么几层：

- **能直读就不 OCR。** xlsx、docx 里的文字是结构化的，直接读比识别准得多，也快得多。Excel 里那些"看起来是数字其实是日期"的单元格（日期序列号），先按单元格格式还原成日期再脱敏，否则会一列日期被打成一串卡号。
- **先判"这块是什么"，再决定怎么脱敏。** 表格不能一律按列头处理：签章区、说明块、"无表头数据"没有列语义，硬套列头就会把"甲方（公章）："当公司列。所以走一个统一的布局分流入口：先剥标题/签章行 → 再判是不是"标签｜值"的 kv 表 → 再定表头 → 然后按布局脱敏。签章、说明这类区域只走文本规则兜底，不给它们瞎套语义。
- **值级 + 文本级双轨。** 表格单元格走"列头语义 + 结构校验"（这一列该是公司就按公司脱敏，形态不像就不脱）；整页自由文本走一串替换器，顺序很重要——先身份证（18 位）再银行卡（13~19 位），否则卡号正则会把身份证吞掉；卡号还要排除"单据号"（PO-2026…0017 这种很容易被误当卡号）。
- **只做一次替换一定会漏。** 同一个证件号换了排版（折行、四位分组、中间插连字符）再出现就匹配不到了；同一家公司名在自由句子里第二次出现、前后没有标点边界，也会漏。所以标准替换完再做两遍扫描：一遍容忍排版分隔符补数字，一遍按"本文件已登记的真实值"精确补码。这样也避免了"每个文本都要匹配一遍脱敏值"导致时间复杂度过高的尴尬局面。
- **一份文件一个追踪器。** 同一真实值在整份文件里必须只用同一个编号/掩码，跨页也一样。否则同一家公司在前页是 CO0002、后页变成 CO0007，AI 会以为这是两家公司，图也会连错。

在这之上还有两个更关键的决定。

**第一个是"编号化"。** 我们不在 hub 正文里留任何明文，只留 CO0001、PT0003、DT0005、BK0002 这样的编号，另有一张映射表解释编号是什么。映射表分两类存：公司、人员、日期是明文可逆的（业务上要能反查）；身份证、银行卡、税号、开户行、账号、项目名、电话只存指纹 + 密文。但是注意，**要给 AI 足够的信息辨别各个编号的所属类别**，不然整份文档的语义都会有问题。

**第二个是"本公司"要单独标出来。** 财务文档里"谁是甲方"直接决定资金方向（应收还是应付）、谁是销方、发票该配哪份合同。所以本公司显示为 `[本公司·CO0001]`，和普通对手方编号区分开，提示词里也专门讲这个标记的含义。

总而言之，AI 能看到的东西，只允许是"脱敏后的正文 + 表结构 + 坐标"。OCR 原始 HTML 行（未脱敏）在写文件前一定要剥掉，不然等于白脱。

## 3. 权限（limitation）

一般不管是教程还是 AI 给的建议中，权限基本不太会特别设计或者提起，但是我当时对一般权限的管理就觉得很混乱。我们固然可以给每个客户一些特定权限，但是要是对方离职要转交权限了呢？难道每一次新来一个人就全部重新规定一次什么能看什么不能看吗？这显然是不太行的。我觉得应该把"业务层"和"客户层"分离，为每个业务层的抽象人员设置权限点。这样客户离职就只要注销客户，业务层还可以赋予新的人。

**客户层（账号）就只剩两件事：绑哪个角色、是否启用。** 于是那个最让人头疼的场景变便宜了：员工离职 → 停用账号（软停用，随时能恢复，审计留痕），角色和权限点一个都不用动；新人来了 → 建账号、绑同一个角色。不用再"重新规定一遍谁看什么"。此外，为了防止隐私泄露，一般新客户都默认最低权限。

## 4. AI 协同部分（AI Cooperation）

由于之前做了脱敏，这一部分显得尤为艰难；又不像正常聊天，财务对准确率要求较高，所以想要达到**成本低、精度高、时间短**，是一件很不容易的事情。首先，全部入库、让接入的 AI 每一遍都去翻找显然是不太可能的办法：10 个文件还好，但公司体量是几百个文件朝上，对话一次还要思考上下文，每对话一次都要烧巨量的 token，准确率还随着量的增多急剧下降。

市面常用的是 RAG 来解决这个问题。然而，RAG 有其无法回避的缺点。传统 RAG 首先要将文字分块、embedding、入库，再在用户问答时根据向量余弦相似度召回拼入提示词。但是首先：**1. 余弦相似度只是语义相似度（甚至不一定），并没有任何逻辑联系；2. 对低频而极重要的词汇极容易缺漏。** 比如一份合同中：甲方：XX 公司（只出现一次），后文并没有这个公司，全都以甲方/乙方来替代，此时我再问 XX 公司的情况，根据 TOPK 的算法是完全召不回来的。第一次实验用的就是 RAG，可惜它的表现实在不尽如人意。

翻阅诸多论文后，我认为一些论文的思路可以借鉴。MAGMA 尽管是长期记忆的方法，但它的因果边、时序边、语义边等"按问询计算的权重找入点走图"的策略，却也是可以在多跳文档中借鉴的。HippoRAG 1/2 专门针对多跳文档开发，确实能有效做到关联段落，然而，对于某一份重要但字数很少的文档，其在遍历中的权重只会降低，在后续图遍历中很容易被忽视；其次它对于文档的概念并不清晰，仅仅关注跨文档段落中的联系。不过尽管有一些问题，这些还是很值得借鉴的思路。

我们可以将**每个文档设为节点 N，对于每个节点，都有子节点 N-K**；其中每一个文档和段落都有唯一的段落 id。为每一个文档 N 进行特征提取，赋予特征哈希以及特征明文；对于文档和段落进行一次概括。这是后续图遍历的基础。虽然各个文档有完全不同的形式，但由于财务规则是一定的，这种多模态文档就会有其一定的导向，这样就省去很多找入点的计算。

我们还发现：**对于每一个项目，表格是这个项目的核心**，从表格出发、以表格为核心可以辐射多条边至各个文档。既然如此，我们就可以干脆从表格出发建立关系边。这里有多种方案：可以用 AI 辅助建边；也可以用图节点权重游走建立弱联系，再在问答时用逻辑链强化。

召回时，图遍历和 topk 节点召回测试后各有 85% 左右的正确率，但是错的方向不太一样。我暂时不采用混合式，而是直接利用 AI 分析用户问题的不同模式进行不同作答：比如直接问"这个仓库里有多少份文件/合同"，就可以直接循环一遍节点，而不必递归走遍历。
